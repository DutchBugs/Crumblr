| AG-012 | HIGH BEFORE REAL AGENT-DRIVEN SUBMISSION / NOT A SHADOW BLOCKER | Raised by Dev 1 (checked the actual `application/live_decision.py` flow, not a guess) while scoping the shared no-MT5 integration path (review 1.26 §7 item 3): `risk.policies.evaluate()`'s `PortfolioState.ledger` (`EquityLedger`) is stateful and per-process — `LiveDecisionOrchestrator` recovers it once via `risk.session.recover_session()` and holds/mutates it in memory across cycles, periodically persisting to `risk_session_states`, rather than reloading before every `evaluate()` call. If this Gateway's proposal path recovered and held its **own** independent copy of that same ledger in a separate process, an internal decision and an external-agent proposal could each pass the daily-loss/drawdown gate against a ledger that doesn't yet reflect the other's most recent trade — a lost-update race on one shared risk budget, invisible to either pipeline on its own. Two resolution paths, in order of preference: (1) route external-agent proposals into the *same running instance* that holds the canonical ledger, rather than a separate process reimplementing `recover_session()`; (2) if a separate process is architecturally necessary, re-recover the ledger fresh immediately before every `evaluate()` call instead of caching it in-process — not race-free without real DB locking, but avoids the worst staleness. **Not a blocker today**: `order_send` is unreachable regardless of which pipeline evaluates a proposal, so no real position can ever result from this gap — but it must be settled for real (most likely option 1) before `feedback.2.0` could ever treat agent-driven submission as real, not discovered live. `CapsuleStore.seal()` (content-derived `capsule_id`, `ON CONFLICT`-safe) and `evaluator.pretrade.evaluate()`'s currently-uncalibrated `intents_in_last_hour` check (`max_intents_per_hour: null` everywhere, F-024) are confirmed **not** to have the same issue today | OPEN — accepted as a shadow-mode-only limitation for the item 3 wiring, option 2 adopted (fresh `recover_session()` immediately before every Gateway-driven `evaluate()` call, never cached in-process) | Option 1 (single shared risk-evaluation authority process) is designed and implemented before any agent-driven submission is treated as real |

| AG-007 | HIGH | Proposal-rate-limit check was a classic check-then-act race: `count_claimed_since` was read in one transaction and `claim_trade_proposal` committed in a separate one, so two concurrent proposals for the same assignment could each observe a stale below-limit count and both get accepted, silently exceeding `max_proposals_per_hour` | **CLOSED — found by a self-review, fixed 2026-08-28** | `PostgresAgentDecisionOutcomeStore.lock_assignment()`/`.transaction()` (`persistence/agent_gateway.py`) — a Postgres transaction-scoped advisory lock (`pg_advisory_xact_lock`) serializes the whole claim→count→evaluate→settle sequence per `assignment_id`; `AgentGateway.submit_trade_proposal`/`submit_no_trade` hold it for the call's duration. Proven both ways: `tests/integration/test_agent_gateway_store.py::TestRateLimitIsAtomicUnderRealConcurrency` (10 real threads, real PostgreSQL, exactly `max_proposals_per_hour` accepted) was manually confirmed to *fail* (10/10 or 7/10 accepted) with the lock temporarily disabled, then re-confirmed green with it restored — the test is proven to catch the regression, not merely pass by luck |
| AG-008 | HIGH | `_replay` (idempotent-retry path) treated "no `REJECTED` event found" as proof of acceptance — a claim interrupted between the claim commit and the settle-event write (crash, exception) left a claimed-but-unsettled row that a retry would silently report `accepted=True` for, without ever running the actual authorization checks | **CLOSED — found by the same self-review, fixed 2026-08-28** | New `AgentDecisionOutcomeStore.settlement_for()` distinguishes "settled `ACCEPTED`/`REJECTED`" from "claimed but never settled." `AgentGateway.submit_trade_proposal`/`submit_no_trade` now resume evaluation with fresh inputs for the unsettled case rather than assuming any particular verdict — genuinely fail-closed, not merely refusing (a raise-based fix was considered and rejected: it would leave the outcome permanently stuck, since every retry would hit the same unsettled state). `agent_decision_events.event_id` also switched from random `uuid4()` to content-derived (mirrors `persistence/execution.py::event_id_for`), so a resumed attempt's re-appended `RECEIVED` event collapses to the existing row instead of duplicating. `tests/unit/test_agent_gateway.py::TestInterruptedClaimIsResumedNotAssumedAccepted` (2 tests) |
